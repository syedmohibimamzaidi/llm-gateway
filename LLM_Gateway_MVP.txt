LLM Gateway MVP
A seven day implementation plan for an AI infrastructure portfolio project
Build one API that accepts a consistent chat request, sends it to either of two configured LLM providers, handles temporary failures, and records usage. The deliverable is a working service with a small analytics page, reproducible tests, and measured behavior. The provider credentials and live model choices are configuration, not hard coded application logic.
Product scope
•  User flow. An application sends a chat request with a gateway API key and a model alias such as fast or smart. The gateway chooses a configured provider, returns a normalized answer, and records the outcome.
•  Success condition. A caller can switch providers without changing the request structure; transient failure triggers bounded retry and fallback; usage and latency appear in the dashboard.
•  Stack. Python, FastAPI, PostgreSQL, Redis, React, Docker, pytest. Use provider SDKs or HTTP adapters behind one internal interface.
Architecture
Client → FastAPI authentication and rate limit → cache lookup → provider router → OpenAI or Anthropic → normalized response. Redis stores rate limit counters and optional cached responses. PostgreSQL stores request metadata, usage, errors, and cost estimates. A React page reads aggregate and request history endpoints.

Request fields: model alias, messages, generation parameters, and optional provider override. Log request ID, key ID, initial/final provider, actual model, input/output tokens, estimated cost, latency, status, retries, fallback reason, cache hit, and timestamp. Do not store prompt or response bodies by default.
Core capabilities
•  Provider interface. Define one generate method and adapters for two providers. Normalize output text, finish reason, token usage, and errors.
•  Routing. Map fast and smart aliases to configured models. Allow an explicit provider override for testing. Keep alias mappings in configuration.
•  Retries and fallback. Retry timeouts, rate limits and transient server errors with bounded exponential backoff; do not retry invalid requests or authentication failures. After retries, try a compatible second provider and record the path.
•  Limits and cache. Apply a per-key Redis rate limit and return HTTP 429 when exhausted. Cache only explicitly eligible, repeatable requests, keyed by provider/model, messages and generation parameters, with a TTL; count a hit without calling the provider.
•  Observability. Record every attempt and final outcome. Calculate cost from a versioned price configuration; mark estimates as estimates, since provider billing may differ.
•  Dashboard. Show request volume, tokens, estimated spend, mean or p95 latency, error rate, cache hit rate, and a provider comparison. Keep the interface functional and compact.
Acceptance checks
Case
Expected result
Valid and invalid key
Valid request succeeds; missing or invalid key is rejected.
Timeout, HTTP 5xx, rate limit
Bounded retry occurs; compatible fallback succeeds when available.
HTTP 4xx validation error
No retry or fallback for malformed input.
Rate limit and repeated request
429 after threshold; eligible repeat comes from cache.
Usage and cost
Stored totals and estimates match fixture token counts and price table.
Simulated load
Record p50/p95 latency, error rate, cache hit rate and fallback recovery; publish actual results only.

Completion and later work
V1 is complete when another developer can start the service, call both providers through one endpoint, reproduce a failure and fallback, inspect usage, and run the tests. Document the provider configuration and publish measured test results. Streaming, semantic caching, complex routing, billing, organization accounts and Kubernetes belong in later iterations.
